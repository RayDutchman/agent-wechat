The agent-wechat server exposes an HTTP API on port `6174`. The active route table below reflects the current router. The detailed audit preserved later in this page is a historical snapshot and is **not** a list of currently registered endpoints.

数据库字段原义、表间关联、通讯录筛选、消息类型及 `server_id` / `local_id` 的统一解释见 [微信数据库与字段字典](/operations/data)。本页维护 HTTP 契约，不另维护一套源数据库语义。

The registration sources are `packages/agent-server-rust/src/router/mod.rs:49–119`, `router/read.rs:1571` onward, `router/send_text.rs:464` onward, and `router/send_file.rs:685` onward. All source references below are relative to `packages/agent-server-rust/src/` unless stated otherwise. Line numbers refer to that revision.

API requests require authentication. The `/health` probe is exempt. A route being registered does not establish that it supplies useful events or that its success response proves message delivery.

## Authentication

```
Authorization: Bearer <token>
```

The middleware also accepts `?token=...`, used by browser WebSockets. A missing or incorrect token returns 401 with `{"error":"Unauthorized"}`. The noVNC **static** paths under `/vnc/` are also exempt; `/vnc/websockify` is not. There is no separately registered `/api/auth` token-issuing endpoint (`router/auth.rs:34–76`).

## Historical HTTP inventory

**Architecture decision for the proposed consolidation:** WeChat login/process state, database snapshots and their lifetime, cursor consistency, voice lookup/retrieval, GUI selection and attachment readiness belong inside this server. A downstream business application should provide account/recipient intent and consume stable results, not reconstruct this server's state machine from epoch, account directories or shard names. The inventory remains a record of today's implementation; the [boundary proposal](#proposed-upstreamdownstream-boundary) below describes changes that are **not implemented**.

Origin **U** means the route already existed in upstream revision `96c2e90`; **I** means it was added by this integration branch in `1f100e0`. This is route provenance, not a claim that every U handler is unchanged. The branch changed legacy read-error reporting in `1f100e0`, selection failure reporting in `9feec95`, and shared database/GUI helper behavior in `baf36ff`. Docker-only `1ee650b` added no API. The totals are **30 U and 8 I**, including the WebSocket registrations listed separately below.

Consumer entries distinguish actual CLI commands and in-repository clients from external applications. External business adapters are not part of this repository: their complete current call graph is **not verified here**. The reported integration uses the dedicated text/file endpoints, whereas the CLI uses the generic sender. This does not establish use of every other endpoint.

Parameters below are path/query parameters unless marked **JSON**, **multipart**, or **header**. Extractor/auth/body-limit errors can occur before the handler and need not use its response envelope. “200 on failure” describes handler-level refusals, not malformed HTTP/JSON. Decoded media uploads are limited to 128 MiB; the global HTTP body allowance includes base64 expansion plus 1 MiB of JSON overhead (`router/mod.rs:39–42,117`).

Chat opening can use the plan's existing popup-dismiss action; it is not a universally side-effect-free selection probe.

V2 page continuation uses the same list endpoint with `cursor`; only `next_cursor: null` is terminal, not a short page. A continuation that omits `q` or `kind` inherits those filters from the frozen cursor sample. If a continuation explicitly supplies a different value—including `q=` to clear a non-empty query—the server rejects it with 409; resource and room identity must also match. The server never recollects or broadens a cursor-only continuation. `release_token` is `null` for single-page results and otherwise stays stable across the frozen sample. The cursor and release token are opaque and expire after the server's fixed in-memory TTL. V2 `ChatV2.username` is the source identity; `last_msg_sender` and `last_sender_display_name` expose the source session sender values (empty strings normalize to `null`). `unread_count` preserves source SQL NULL as JSON `null`, and retains all integer values otherwise. No V2 endpoint falls back to a V1 response.

V2 native message lookup/media/voice requests use optional `chat_username` to scope the message locator; the old `conversation_username` query key is rejected as an unknown parameter. `POST /api/v2/messages/send` requires a non-empty `chat_username` string and returns nullable `chat_username` in its result; the old request key is rejected (`400 invalid_parameter`) rather than aliased. `ReferenceV2.chat_username` is nullable and is the only serialized reference chat-name key. `MessageV2.chat_username` remains the required identity for the containing message.

Message V2 filters use `include=[{"type":49,"sub_type":6}]` and `exclude=[{"type":10000}]` as URL-encoded JSON arrays. An omitted `include` means all types; `include=[]` means none. Entries within a list are ORed, include/exclude dimensions are ANDed, and exclusion wins. A sub-type requires a type and matches only that type; unknown non-negative u32 codes are accepted and preserved. Cursor-only continuation inherits `order` and filters; explicitly changed order/include/exclude gets 409. The CLI `--config` JSON file accepts only the `include` and `exclude` arrays. Type labels come from the canonical `packages/agent-server-rust/src/message-type-dictionary.json`, also compiled into the Docker Rust source context and transformed by `scripts/generate-types.sh` for the shared/CLI module. Namespaces `main`, `appmsg`, and `forwarded_inner` are separate; each entry has numeric `code`, stable English `key`, Chinese `label`, and `basis` (`default_adopted` or `local_observed`). Unknown numbers remain numeric and are rendered as unknown, never coerced to text.

`MessageV2.server_id`, `local_id`, and `raw_type` are decimal strings (zero/missing message IDs are `null`); `type` and `sub_type` are the low/high u32 portions of the stored i64 bit pattern. `timestamp` retains the valid RFC3339 value produced from source `create_time`. In V2 frozen message collection, a missing or non-integer `create_time` rejects the row before projection; it does not produce a successful message with a null timestamp. An integer outside Chrono's representable range follows the existing collector path that yields an empty timestamp, which the V2 projection emits as `null`. The legacy message projection is unchanged. The `raw_content` field remains the frozen sample's opaque retained hex representation; it is not decoded business XML. Required `raw_content_compression` is the original row's boolean compression flag and must be paired with those bytes; callers must not infer it from decoded content or a missing value. `content` keeps the legacy clean/display behavior. `xml_sub_type` is decoded independently from the source XML and can differ from packed `sub_type`; neither value rewrites the other. `reference` preserves `svrid` as source text (including `"0"`), the referenced chat identity, the referenced `chatusr`, and the stored `displayname` separately. In group references, `fromusr` supplies the chat identity; in direct chats the current chat context supplies the chat, while a missing `chatusr` remains missing. No author is inferred from a display name or `fromusr`.

For app-message subtype 19, `forwarded_record` contains ordered `items` with `datatype`, `dataid`, `datadesc`, source display fields and lexical time/message-ID strings. `dataitem_source_hash_username` is only the source hash value, not an addressable username. `parse_status` is `complete`, `truncated`, or `invalid`; a truncated item-count/text limit retains only the complete prefix, while malformed XML returns no items. The parser accepts only the bounded message-record XML subset: at most 4 MiB after decode, nesting depth 16, 20,000 XML nodes/events, 100 entries, and 64 KiB per entry description. It rejects DTD/entity declarations and does not resolve external resources. This is not a general-purpose XML parser; unfamiliar XML shapes may report `invalid`. No nested messages are scheduled, no source URLs are fetched, and forwarding fields do not change `content`, media policy, or send behavior. The CLI JSON output retains the full snake_case V2 fields; readable output labels the inner type without treating it as an outer message type.

Native lookup scans only validated `Msg_<32 lowercase hex>` tables in the currently captured account scope, binds the ID as a SQL parameter, and refuses multiple matches. Media and raw voice use that exact internal source anchor; callers never supply shard/local ID/epoch. Existing local-ID media and send routes remain available and unchanged. The CLI supports native media via `wx messages media <chatId> --server-id <id>` while retaining the existing positional local-ID form; raw voice has no CLI input/command in this change and no send route was added.

## Send API comparison

These are three existing entry points, not three levels of delivery confirmation. `chatId` is the **recipient** identifier; the response's `accountId` describes the captured **sender account storage identity**. They must not be substituted for one another. In particular, this `accountId` is derived from the account directory, not independently read as a UI-proven wxid (`tools/wechat_read_identity.rs:413–438`).

### What the extra fields actually establish

| Field or check | Fact checked today | What it does not establish |
|----------------|--------------------|-----------------------------|
| Current account identity | Which account is represented by the chosen identity source; today's `accountId` is storage-derived | A separate UI-proof of login, or whether the process/session is the same generation as an earlier observation |
| Native current chat identifier versus `chatId` | Which chat is selected | Sender identity, upload integrity, or delivery |
| `expectedEpoch` | Whether the caller's earlier identity scope still matches the server's current scope | Recipient permission or a requirement that a queued send must be cancelled after every same-account re-login |
| `sha256` | Decoded upload bytes match the caller-supplied digest | Approval, recipient identity, or receipt by WeChat/the recipient |
| `size` | Decoded byte count matches the caller-supplied count | Anything about which file the caller intended, beyond that length |
| Empty composer / paste result / enabled Send | Local preparation observations | Correct destination or delivery; these are separate from identity checks |

The server can compute size and SHA-256 itself. Caller-supplied values add an independent business check only when tied to an independently approved artifact; values computed from the same bytes immediately before upload mainly check request self-consistency. Neither replaces the other as a byte-level check, and neither replaces account/chat identity checks.

**Decision notes, not implemented changes:** the proposed unified API validates the intended sender wxid and current recipient internally without requiring a caller-supplied epoch. Keeping internal checks across a single operation is separate from requiring the caller's previous generation token. No business requirement established by this API audit says that a queued send must be rejected solely because the same account logged in again. The same boundary applies to reads: downstream callers pass opaque cursors/media handles, rather than epoch/account-directory/shard details. The epoch inventory below distinguishes current behavior from the proposed internal responsibility. None of these alternatives has been implemented by this documentation update.

The dedicated file endpoint's `target_changed` is not limited to an actual recipient change: its plan also uses that code when the pane/composer preparation check fails **before** consulting the identity fence (`SendMessagePhase::ReadyToCommit` in `plans/send_message.rs`). Removing `expectedEpoch` alone therefore does not address every file-send refusal with that code. A caller that discards `commitAttempted` cannot reconstruct it from the error code later.

### File-name handling

Both CLI and dedicated file requests carry a basename, but the handlers stage it differently. The legacy route replaces non-ASCII characters and prefixes the temporary filename with a timestamp. The dedicated route validates the basename and preserves it inside a private upload directory owned by the session's operating-system user.

The common `docker/tools/launch-wechat` launcher sets `LANG`, `LC_ALL` and `LC_CTYPE` to `C.UTF-8`. With this startup environment, `docker/tools/paste-file` pastes the original file URI without creating a renamed alias. Dedicated uploads retain their staged basename through clipboard preparation; the legacy route's own filename rewriting remains unchanged. A successful helper exit alone does not confirm that WeChat accepted or sent the attachment.

## Local-read contracts

Chat, contact and message-list reads (including chat/contact search and single-chat lookup) return `{"error":"CODE","code":"CODE"}` when a read cannot be completed:

| HTTP status | Code |
|-------------|------|
| `503` | `WECHAT_SESSION_UNAVAILABLE` |
| `409` | `WECHAT_NOT_LOGGED_IN` |
| `503` | `WECHAT_KEYS_UNAVAILABLE` |
| `500` | `WECHAT_DB_READ_FAILED` |

Successful responses keep their array or single-chat object/`null` shape. A failed candidate-database lookup or a missing key for a discovered message database fails the request instead of silently skipping that source. An empty array is not proof of complete history; pagination and source coverage still apply. Media reads retain the media-specific results described below.

Database reads are source-isolated: the reader copies the database file and its write-ahead log as ordinary file bytes, merges the valid committed prefix, and opens only a private encrypted copy with SQLite. The live client database is therefore never opened by SQLite, locked, checkpointed or rewritten by this read path, and the read needs no source `-shm`. Every rowid is the source's, including implicit rowids of tables without a primary key. Invalid WAL headers fail the read; frame validation stops at the first invalid frame, and only commits in the preceding valid prefix are merged. A copy with no valid committed frames is not proof that the client has no newer messages. A read whose database, write-ahead log, merge index and merged copy together would exceed 512 MiB is refused rather than read, and a source that changes while it is being copied is refused rather than returned half-updated. This is a per-build processing budget, not a process-wide memory limit. This path verifies a page's SQLCipher HMAC when the page is read; it does not authenticate every logical page up front.

Unchanged database/WAL file metadata and the same key allow reuse of a private encrypted copy; each caller opens an independent SQLite connection. The four-entry source-copy cache is separate from the frozen pagination samples below. Graceful shutdown clears retained copies, while abrupt termination can leave private files; this does not provide incremental WAL updates or remove other processes' files.

The contact roster shares that envelope and these error codes, but its scope is fixed and independent of any chat: a roster cursor cannot read a message sample and a message cursor cannot read the roster. Each roster item is exactly five string fields — `username`, `remark`, `nick_name`, `alias`, `display_name` — read from `contact.db` (`WHERE delete_flag = 0`, `alias` only when the live schema has it). The first-page limit is 1–1000 (default 100). Pages also have a 3 MiB serialized-items ceiling, so a short page is not terminal: follow `nextCursor` until null. Budgets: four retained snapshots, 50,000 rows/16 MiB per sample, 32 MiB total serialized row data; single-page samples need no retained cursor cache. Capacity exhaustion rejects new snapshots with `413` instead of evicting unexpired cursors. Release after completion or abandonment. If release fails, retain the successful read result and let TTL reclaim the cache; do not replay business actions.

Requests have an 8-second round budget, including at most 2 seconds waiting for the UI guard; collection interrupts SQL and caps decompressed content at 4 MiB per row. Missing keys, unreadable shards and invalid rows fail the request rather than return partial data. An unverified login write blocks identity reads until a successful login-state write advances the generation. These endpoints do not initiate key extraction or UI actions.

### Fenced text send

`POST /api/send/text` accepts only `{chatId,text,expectedEpoch}`. It holds the shared UI guard and rechecks the account epoch and selected chat before dispatching Return. Text and epoch must be nonempty; image/file fields are rejected.

The execution response is `{success,accountId,epoch,chatId,commitAttempted,uiConfirmed,errorCode?}`. A refusal after the pre-checks reports `200` with `errorCode` `chat_not_open` (the focus round did not observe an open chat, which is not attributable to a single cause), `chat_selection_failed` (the chat selection helper did not answer with success), `scope_changed`/`target_changed`/`composer_not_empty`/`paste_failed`, `aborted`, `timeout`, `execution_failed` or `commit_unconfirmed`. HTTP 200 or `uiConfirmed` alone does not prove a new message or recipient delivery: reconcile newly observed outgoing records against a pre-send baseline. After a timeout or uncertain commit, do not automatically repeat the POST. This endpoint does not provide an idempotency key.

### Fenced file send

`POST /api/send/file` accepts only `{chatId,expectedEpoch,filename,data,sha256,size}`: one file, no caption, no host path or image field. `data` is standard base64, `sha256` is a lowercase 64-character hex digest, and `size` is the exact decoded byte count. `filename` must be a single basename (no `/` or `\`, no control byte, not `.` or `..`); the original name is preserved at staging and by the paste helper. The decoded bytes must not exceed the 128 MiB upload limit and must match both `size` and `sha256` before any client work starts.

The file is staged in an exclusive `0700` directory as a `0600` `create_new` file owned by the trusted session's login user (resolved from `/etc/passwd`, never from the request) so the WeChat user can read it, and removed on every path. A missing session or unmapped login user is refused before staging; owner-setting failure is a pre-commit `temp_storage_failed` and its own staged paths are cleaned up. Before pasting, the run requires an empty composer — an editable field whose accessibility helper reports the derived `TEXT_EMPTY` state (the AT-SPI Text character count, never the field's label) with a disabled Send control — and records that baseline; an occupied composer is refused with `composer_not_empty` and is never cleared. The paste runs on the fenced session's display with a bounded deadline and must exit zero, otherwise the run is refused with `paste_failed` and nothing is committed; the attachment is committed by a separate Return step only after the baseline, the successful paste, the live readiness, and the account epoch plus selected chat all still hold. Sending holds the shared UI guard, and dropping the request cancels an uncommitted run before Return.

The response is `{success,accountId,epoch,chatId,commitAttempted,uiConfirmed,errorCode?,payloadSha256,payloadSize}`. Pre-check failures use `400 invalid_parameter`/`invalid_filename`/`invalid_encoding`/`payload_mismatch`, `413 payload_too_large`, `500 temp_storage_failed`, `409 scope_changed` or `503 identity_unavailable`/`not_logged_in`/`login_unverified`/`target_unavailable`/`deadline_exceeded`; execution/post-check refusals report `200` with `errorCode` `composer_not_empty`/`paste_failed`/`target_changed`/`scope_changed`/`identity_unavailable`/`chat_not_open`/`chat_selection_failed`/`aborted`/`timeout`/`execution_failed`/`commit_unconfirmed`. `payloadSha256` and `payloadSize` attest only the accepted upload, not delivery, and neither the staged file's deletion nor `uiConfirmed` proves the client read the bytes; reconcile outgoing records and never auto-repeat an uncertain commit.

## Media quality and generic-send details

For image media, `?quality=full` requires the original-resolution copy,
`?quality=standard` requires the mid-size copy, and `?quality=thumbnail`
requests the preview. `?quality=best` returns the best valid local copy.
When the message advertises an Original image, it requests the native full-size
transfer and waits up to 20 seconds before returning the best cached fallback.
Its `quality` response field is `full`, `standard`, or `thumbnail`. A regular
phone send may advertise only a standard image; opening its chat can make
WeChat cache that copy. The media endpoint does not open chats itself. Without
the standard copy, `best` returns a thumbnail and strict `standard` has no
image data yet. Omitting `quality` now uses `best`; pass `quality=full` to
require the original-resolution copy.

`POST /api/messages/send` is unfenced and returns `{success,error?}`. It reports
what it observed without remapping it: `NOT_LOGGED_IN` for a login refusal,
`No session available` when there is no session, `No text, image, or file
provided` for an empty body, and otherwise the run's own error — which is
`chat_not_open` or `chat_selection_failed` when the send stopped waiting for an
open chat or for a successful chat selection, and the historical text
(`No action selected`, `Aborted`, `Execution timeout after Ns`,
`Unknown state for Ns - no matching IAState found`, `Max steps reached`)
otherwise.

The legacy JSON shape does not enforce mutual exclusion of text/image/file: use one kind rather than relying on the plan's branch priority. File base64/write failures return `success:false`; image decode/write failures can instead leave no image path and fall through into the plan (`router/messages.rs:434–511`). The Rust `SendResult` contains no `messageId` (`ia/types.rs:541–546`), even if a client-side convenience type suggests one. These details are current behavior, not a recommended new result contract.

## Epoch inventory and simplification decisions

### What changes an epoch

This epoch is a 64-character SHA-256 digest, **not a Unix timestamp, authentication token, permission generation, or message version**. It was introduced with the reliable-read/dedicated-send APIs in `1f100e0`; it is not a parameter of every endpoint.

`epoch_of` hashes a domain separator followed by seven NUL-separated fields: `login_generation`, canonical session row id, WeChat process PID, process start tick, boot id, account-directory name, and full database-root path (`tools/wechat_read_identity.rs:440–470`). The server's own PID is not one of these fields.

| Event or fact | Implemented effect | Evidence |
|---------------|--------------------|----------|
| Successful login-identity write, even the same account value | Increments `sessions.login_generation`; therefore changes epoch | `db/queries.rs:611–712`, specifically `674–691` |
| Successful logout-identity write | Also increments generation; logged-out state cannot yield a usable logged-in identity | `router/status.rs:185–199`; same writer |
| Login write fails or cannot be verified | Quarantine marker blocks trusted identity capture, typically 503 `login_unverified`; it does not grant a new usable epoch | `db/queries.rs:630–709`; `tools/wechat_read_identity.rs:362–378` |
| WeChat process replaced, boot changed, session row replaced, account directory/root changed | Changes a hashed field and hence epoch, even if the displayed account name/wxid is unchanged | `tools/wechat_read_identity.rs:440–470` |
| Only agent-server restarts, with all seven facts unchanged | Does not itself change the digest; **in-memory cursor caches are nevertheless lost** | Same hash inputs; `tools/wechat_read_pages.rs` in-memory store |
| External UI logout/login without the recorded login write, with process/root unchanged | May not change epoch; it is **not continuous proof of every UI login transition** | `tools/wechat_read_identity.rs:20–26` |

The generation is advanced by the login plan and logout handler through `update_session_logged_in_user` (`plans/login.rs:266`, `router/status.rs:189`); it is not a counter that ordinary polling increments. Migration `V4__session_login_generation.sql:12–18` initializes existing logged-in rows to generation 1. The account ID derivation is a storage-layout mapping, not a new UI authentication mechanism (`tools/wechat_read_identity.rs:413–438`).

### Where epoch is not used

Legacy chat/contact/message/media endpoints, `/api/messages/send`, session management, status/debug, and VNC/events do not require `expectedEpoch`. Login/logout **update the generation** but do not ask the caller to provide one. Outgoing voice jobs use account ownership, idempotency, a shared GUI guard and destination selection; they have **no epoch field or `LiveSendFence`** (`router/voice.rs:39–44,58–218,265–298,323–359`). There is no separate epoch-based contact permission system in this repository.

### Decision summary — recommendations, not changes

- **Sending:** consolidating on one sender and removing its caller-supplied `expectedEpoch` is a viable design candidate, not an implemented patch. It requires an explicit intended-sender identity check, not just checking recipient `chatId`. Re-login of the same account changes a recorded epoch, but this audit establishes no business requirement to reject a queued send solely for that reason.
- **Reading:** keep frozen-row reuse, resource-scoped cursors, scoped release, source consistency and before/after identity checks internally. An old cursor must not become valid merely because the same wxid is logged in again. Remove public `expectedEpoch`/account-directory/shard prerequisites in the proposed simplified contract; retain their necessary internal guarantees through server-owned state and opaque handles. Migration still requires approval.
- **Redundant API surface:** generic sending overlaps dedicated text/file sending; legacy message/contact listing overlaps frozen reads but differs in pagination, coverage and refusal semantics. Login QR polling overlaps part of the login WS presentation, but only WS runs the login plan. Voice jobs are a separate asynchronous operation, not an interchangeable file-send response.
- **Potential removal scope if consolidation is approved:** the two dedicated route registrations, request/response validation and route-specific tests can be removed together. `send_file.rs` currently imports identity/error/fence helpers from `send_text.rs`; plan fence branches are used by both dedicated routes. They are not independent one-file deletions. Preserve the shared execution loop/GUI guard, native chat selection, general send plan, upload limits, media helpers, voice jobs and identity/paging code needed by reads. Any useful checks retained for unified sending need moving before their old modules are removed (`router/send_file.rs:69–73`; `plans/send_message.rs:12–65,999–1042`; `execution/mod.rs:28–82`; `router/mod.rs:39–42`).

Separating file-readiness refusals from target changes and preserving filenames in the legacy route remain follow-up work. Dedicated Chinese-filename delivery has been verified on the tested client build with the UTF-8 launch environment; this does not establish compatibility with every filename or client build. This inventory does not authorize deleting endpoints, changing gates, sending a diagnostic message, or treating unit tests as a new live-send acceptance result.

## Proposed upstream/downstream boundary

**Direction approved; endpoint/schema migration not implemented.** The API should expose stable account wxids, contact/message identities, content/files/audio, and explicit operation results. Internal identity generations and source layout remain the server's responsibility. In particular, today's storage-derived `accountId` must not simply be relabelled “verified account wxid” without establishing the identity source.

### Proposed account check sequence

1. The downstream request expresses **expected account wxid** and recipient `chatId`, alongside the content or opaque cursor/media handle. The proposed account field describes intent, not a process generation; clients do not manufacture epochs or shard names.
2. For sends, the server acquires the shared GUI guard, resolves the actual account and rejects a different account **before preparing content**. It selects and verifies the recipient, prepares the composer/attachment, and rechecks account and recipient immediately before dispatching the send action.
3. Internal process/session changes can invalidate a prepared operation or a read handle. The server handles that state transition and reports a specific refusal/expiry; it must not silently reinterpret an old request as belonging to another account. Re-login of the same account before preparation is not, by itself, a business revocation of queued intent.
4. After a possibly attempted send, the server reports the evidence it actually has. If the outcome is unknown, it remains unknown; account drift or a failed post-check cannot undo an action already dispatched. The downstream keeps its task, recipient authorization, queue, single-submission policy and send ledger, and does not blindly retry.

Reads follow the same account-intent boundary without requiring business callers to understand snapshot internals. An opaque cursor or media handle must be validated by the server; passing it back unchanged is not permission to reinterpret it for another account. HTTP 200 remains a transport/handler result, never a blanket promise of WeChat delivery.
