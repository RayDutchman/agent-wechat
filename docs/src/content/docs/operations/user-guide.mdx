Examples use the default container `agent-wechat`, session `default`, and port `6174`. Replace these when using a different deployment. Runtime image labels and database sizes are installation-specific, not guarantees of this guide.

See the [CLI command reference](/getting-started/cli/commands) for command syntax and options. This guide focuses on operational workflows and behavior.

## Start and inspect

```bash
wx up
wx auth login
wx status
wx chats list
wx logs
```

Complete any phone confirmation and wait for the login command to finish. An interrupted command is not proof that the server-side operation stopped; check the existing flow before starting another. The number of chats depends on the account.

`wx status` checks container/server availability and the V2 account observation. `wx auth status` also uses that account API. Login status is a UI observation; an unrecognized UI is `unknown`, not proof of login. The old `/api/status` and `/api/status/auth` reads are retired.

The health monitor restarts WeChat after its process disappears, with a short delay and a longer delay after repeated rapid restarts. A live process that is stuck is no longer killed automatically; `account GET` remains an observation of the UI and can report `unknown`. A user-closed WeChat process also looks like a disappearance and may be restarted; use `wx session stop <id>` to disable monitoring for that session. Missing decryption keys remain a `503 keys_unavailable` on the first read; qualifying reads and classified authentication failures schedule bounded, background key recovery. Identity-unknown cases do not trigger extraction. This recovery does not promise to bypass account restrictions or risk controls.

For an existing container, `docker stop agent-wechat` and `docker start agent-wechat` stop and start it. Coordinate these with connected automation. `wx down` removes the container while retaining its data volumes; it is not the same operation as stopping it.

## Read chats, contacts, and messages

Use returned chat identifiers rather than assuming names are unique. Message IDs use the native `server_id`; `local_id` is an internal row locator and is not globally unique. These reads use V2 cursor pagination. `--all` follows pages serially and releases its retained sample when finished; a short page is not necessarily the last page. See the [CLI command reference](/getting-started/cli/commands) for paging options and the [API reference](/reference/api) for cursor and response contracts.

Message filters can be supplied through the optional JSON `--config` file. The API reference documents the filter and V2 field contracts; the [database field dictionary](/operations/data) documents source-field meanings and message types.

## Retrieve media

Use the [CLI command reference](/getting-started/cli/commands) for media command syntax and options. The default image quality is the best available; strict original-quality requests can remain unavailable. A `pending` result should be retried with a bounded policy. A JPEG returned for a video is only a preview, not the video itself; message XML or an empty result is not an attachment.

Opening a chat may let WeChat cache media in visible history; it does not guarantee downloading every attachment. The media endpoint itself does not select a chat.

## Send and inspect voice jobs

Confirm the destination before sending. GUI-changing automation is serialized by the server, but manual desktop input is not covered by that guard.

```bash
wx messages send <chatId> --voice /path/audio.wav --detach
wx messages voice status <jobId>
wx messages voice cancel <jobId>
```

Synchronous text/image/file sends use one `POST /api/v2/messages/send`. If several are provided, exactly one is selected in file > image > text priority; the CLI reports ignored fields on stderr, and `--json` writes only the V2 response JSON to stdout. This is not a multi-message or caption feature. `success`/`ui_confirmed` describe local UI confirmation, not remote delivery. A timeout or incomplete HTTP response is uncertain; do not blindly retry.

Voice jobs can partially succeed; `needs_review` requires checking what was actually sent. V2 file sends preserve the supplied basename after server-side validation.

## Sessions and debugging

Use the [CLI command reference](/getting-started/cli/commands) for session and diagnostic command syntax. The global `-s` option selects a session for a command.

`wx session delete <id>` can remove the session's Linux user and home data. It is not a logout command. Screenshots and accessibility trees may contain private messages; keep diagnostic files outside the repository.

## HTTP access

```bash
TOKEN=$(tr -d '\r\n' < ~/.config/agent-wechat/token)
curl -H "Authorization: Bearer $TOKEN" http://localhost:6174/api/v2/chats
```

Keep the token and authenticated viewer URLs private. The [API reference](/reference/api) is the maintained route inventory. In particular, `/api/ws/login` drives the login flow; `POST /api/status/login` only inspects a QR screenshot.

The change subscription is available through `wx events watch` when the matching server and file-watcher helper are installed; see the [CLI command reference](/getting-started/cli/commands). The CLI and shared `subscribeChanges({ signal, onStatus })` only listen and reconnect: they do not read messages or invoke a model. Notifications are not replayed or guaranteed, so integrating consumers must arrange their own catch-up read at startup and after reconnect. See the [API reference](/reference/api) for WebSocket authentication and event details.

The decoded upload limit is 128 MiB; the HTTP body allowance accounts for base64 expansion and JSON overhead. This does not impose the same size limit on downloaded attachments or source databases.

## Build compatibility and coordinated updates

A successful host `cargo build` does not prove that its binary can run in the container. A host-linked binary requiring newer glibc symbols can fail before the server starts. Use the repository's container build environment (currently `rust:1.93-bookworm`), then verify the resulting executable in the exact target runtime image with no account, production mounts, or published ports. Check both dynamic-library loading and an actual server startup; `ldd` alone is not an application smoke test.

Before updating a running deployment:

1. Coordinate a pause with connected automation and drain in-flight work. Preserve the current binary, helper presence/bytes, ownership, mode, container settings and account identity. Source commit and image tag alone do not identify a hot-replaced executable.
2. Install the server and `watch-wechat-data.py` as a compatible set; an unchanged helper needs verification rather than another write. Stage on the same filesystem, verify bytes and metadata, then replace the target path.
3. Signal only the intended server process. Check the entrypoint's actual supervision behavior: a replacement that cannot start can terminate the container and its WeChat process even if the old server exited gracefully. Stop on failure rather than repeatedly restarting.
4. Verify the new process executable, health, expected account and minimal authenticated V2/WebSocket operations. A successful handshake does not prove that a real message was delivered by an event instead of a periodic catch-up read.
5. If recovery requires starting a stopped container, coordinate that separately: it restarts WeChat and may require phone confirmation. Restore only the authorized artifacts, record any retained helper, and let the automation owner decide when to resume. Do not retry uncertain messages as part of recovery.

Keep installation-specific hashes, acceptance evidence and backup locations in private local records, not public source or credentials in command examples. Preserve the known-good artifacts until the new deployment has been accepted.

## Desktop access and history import

See [VNC Viewer](/operations/vnc) for the authenticated URL, temporary interactive access, and how to restore read-only mode. Keep the image's read-only default.

For phone chat history, use the WeChat client's own migration or restore facility if supported by the installed client. Do not substitute direct database-directory replacement. Prepare the operation in this order:

1. Pause connected receivers, senders, and background jobs; ensure no in-flight model/tool operation can send during migration.
2. Establish how imported history will be recorded without executing old messages. Existing chat checkpoints may interpret newly assigned local IDs as new input; first-start history handling alone is not a migration guarantee. Do not erase checkpoints to force a rescan.
3. Make coordinated, consistent backups of both actual container data mounts and the connected application's ledger. Merely archiving active database files is not a consistency guarantee. Record the runtime version and mount mapping needed for recovery.
4. Enable temporary interactive VNC and first migrate a small selected chat through the client's UI. Verify old/new message timestamps and sample attachments in WeChat before expanding the import.
5. Check the imported data through the API and inspect the largest database. The 512 MiB snapshot-processing budget includes the source database, WAL, merge index, and merged copy; it is not a promise that arbitrary multi-gigabyte databases are supported.
6. Apply the agreed history-only baseline, restore read-only VNC, and resume automation only after imported records are excluded from automatic replies or historical command execution.

This is a preparation workflow, not a claim that cross-platform history migration has been verified for every WeChat build. Volume names, backup procedures, and application baseline handling must match the actual deployment. See [Data & Storage](/operations/data).

Host networking alone does not guarantee phone discovery or history transfer. Preserve the deployment's network mode, capabilities, data mounts, token and runtime version when recreating it; verify reachability on the target host. See [Environment Variables](/reference/environment-vars) and [VNC Viewer](/operations/vnc) for listener configuration. A successful migration does not guarantee that every historical message type is parsed; retain parsing failures and backups until recovery and application checks are complete.
