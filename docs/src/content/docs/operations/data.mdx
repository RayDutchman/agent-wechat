This page is the unified reference for this project's interpretation of local WeChat data. For HTTP parameters and response contracts, see [REST API](/reference/api). Update this page first when field meanings are confirmed; do not create a parallel dictionary.

Applies to Linux WeChat **4.1.13.23**. Organized by database, table, source field, relationship, and API mapping; fields not exposed by the API are also included in the schemas.

## Storage locations and database overview

Two persistent volumes are used by default. Deployments can customize their names; use the actual mounts as the source of truth:

| Volume | Container path | Contents |
|--------|---------------|----------|
| `agent-wechat-data` | `/data` | This project's `agent.db`; the authentication token is mounted separately as a read-only file |
| `agent-wechat-home` | `/home/wechat` | WeChat account databases, attachments, configuration, and cache |

The account directory is usually `/home/wechat/xwechat_files/<account_directory>/`, with databases in its `db_storage/` subdirectory. The directory name is not the profile nickname and is not independent proof of UI login.

| Path relative to `db_storage/` | Primary use | Coverage in this page |
|---|---|---|
| `contact/contact.db` | Contact, group, and official-account profiles | Schemas for six documented tables and verified semantics |
| `session/session.db` | Local conversation list, summaries, unread counts, and ordering | Complete `SessionTable` schema, 19 columns |
| `message/message_N.db` | Sharded chat history | Complete column list for one actual `Msg_*` table and current query rules |
| `message/media_N.db` | Voice data and relationships | Columns used from `VoiceInfo` and `Name2Id` |
| `message/message_resource.db` | Message-to-media-resource index | Columns used from `ChatName2Id` and `MessageResourceInfo` |
| `hardlink/hardlink.db` | Attachment path index | Columns used from image-related tables |
| `message/biz_message_N.db`, `message_fts.db`, `weclaw.db` | These files have been observed; their fields have not been fully examined | Do not infer that they share the schema of ordinary message shards from their filenames |
| `head_image/`, `emoticon/`, `favorite/`, `sns/`, `general/`, etc. | Related storage for profile images, stickers, favorites, Moments, and other data | No field-by-field dictionary yet |

Much of the image, video, and file data is stored under paths such as `msg/attach/`, `msg/video/`, and `msg/file/` in the account directory; it is not all stored in `message_N.db`. A `.dat` suffix does not mean the file is an ordinary plaintext image.

### The project's own agent.db

- `/data/agent.db` is this project's SQLCipher database. It stores sessions, application state, acquired credentials, and job information; it is not WeChat's `contact.db` or message database. Table definitions are maintained in `packages/agent-server-rust/migrations/`. Tables such as `sessions` and `wechat_keys` are not native WeChat fields.
- `/data/auth-token` is a read-only mount of the host token; it should not be included in images or public documentation.

## contact.db: contacts, groups, and official accounts

The following are source fields from six tables; types are recorded as declared in the actual schema.

### `contact` table

| Source field | Source type | Meaning and current use |
|---|---|---|
| `id` | INTEGER PRIMARY KEY | Internal integer ID for this table, not `username`; verify the specific relationship before using it across tables |
| `username` | TEXT | Source identifier for an account, group, or system entry, passed through unchanged; it is not guaranteed to start with `wxid_` |
| `local_type` | INTEGER | Contact-record type; the same-named message-table column uses a different enum, as described below |
| `alias` | TEXT | “WeChat ID” shown on the profile page and usable for login; stored separately from the internal username |
| `encrypt_username` | TEXT | Observed column; purpose and encoding are unconfirmed |
| `flag` | INTEGER | Raw bit flags; the complete bit dictionary is unconfirmed. Do not use `flag & 2` to determine friendship |
| `delete_flag` | INTEGER | The current broad roster selects only 0; this does not prove a mutual friendship or that the other party has not deleted this account |
| `verify_flag` | INTEGER | Raw value related to verification or special accounts; full bit semantics are unconfirmed. See below for the observed relationship with bit 8 |
| `remark` | TEXT | Remark this account assigned to the contact |
| `remark_quan_pin` | TEXT | Observed column; the name suggests pinyin used for remark search, but exact behavior is unverified |
| `remark_pin_yin_initial` | TEXT | Observed column; exact pinyin-abbreviation behavior is unverified |
| `nick_name` | TEXT | The editable profile-page “name” supplied by the other party, not this account's remark |
| `pin_yin_initial` | TEXT | Observed column; exact search-generation behavior is unverified |
| `quan_pin` | TEXT | Observed column; exact search-generation behavior is unverified |
| `big_head_url` | TEXT | Large profile-image URL |
| `small_head_url` | TEXT | Small profile-image URL, directly exposed by an older contact projection; not exposed by current ContactV2 |
| `head_img_md5` | TEXT | Profile-image digest identifier; nonempty values are 32-character strings. Preserve the source value; do not use it as the MD5 checksum for a currently downloaded profile image |
| `chat_room_notify` | INTEGER | Group notification setting: 0 = notifications off (Do Not Disturb enabled); 1 = notifications on (Do Not Disturb disabled) |
| `is_in_chat_room` | INTEGER | 0 or 1: still in the group; 2: left the group. Do not determine membership using 0/nonzero; the exact distinction between 0 and 1 is unresolved |
| `description` | TEXT | “Memo” text this account added to the contact, stored separately from nickname and remark |
| `extra_buffer` | BLOB | Additional binary data; format not fully parsed. Do not conflate it with the group table's `ext_buffer` |
| `chat_room_type` | INTEGER | Raw group-related category; observed values are 0 and 2. Meaning is unresolved; do not infer admin settings or join rules |

Current ContactV2 retains `username/alias/nick_name/remark/local_type` and adds `kind`, `display_name`, and optional `official_type/verify_flag`. `display_name` is derived using `trim(remark)` → `trim(nick_name)` → the original username as fallback. Source name fields remain separate; the derived display name is not treated as a canonical name. `flag` and `delete_flag` are not exposed directly as ContactV2 fields.

### `kind`, address-book membership, and mutual friendship are distinct

The current `kind` classification priority is: fixed system list → `@chatroom` group → `@openim` enterprise → official account with nonempty `biz_info.type` → `local_type=5` enterprise and `1/3` individual → unknown. Therefore, `kind=individual` is **not a friendship indicator**. A separately researched rule for type 6 has not been added to the classifier; current type-6 records with `@openim` are identified by the suffix.

Fixed system list: `filehelper`, `fmessage`, `medianote`, `floatbottle`, `newsapp`, `fenvmsg`, `officialaccounts`, `weixin`, `weibo`, `qqmail`, `brandsessionholder`, `brandservicesessionholder`. This is not an exhaustive list of all WeChat system accounts. `@weclaw` has been observed as a special ClawBot account, though its current `kind` may still be `individual`.

**Ordinary address-book filter**: Among valid records with `delete_flag=0`, select `local_type=1` and exclude the current account, system entries, groups, enterprises, ClawBot, and known official accounts.

Consumers of current ContactV2 can apply this after validating a successful response:

```python
# SYSTEM_USERNAMES is the fixed list above; account_username comes from the trusted current account.
def is_ordinary_address_book_contact(contact, account_username):
    username = contact["username"]
    return (
        type(contact["local_type"]) is int
        and contact["local_type"] == 1
        and contact["kind"] == "individual"
        and username != account_username
        and username not in SYSTEM_USERNAMES
        and not username.endswith(("@chatroom", "@openim", "@weclaw"))
        and contact.get("official_type") is None
    )
```

`official_type=0` is still a valid official-account type; do not write this as `not official_type`. The upstream query already filters `delete_flag=0`; consumers should not require a `delete_flag` field that is absent from the DTO. This predicate represents the local ordinary-address-book definition and does not detect whether the other party deleted this account.

Classification rules:

| Field combination | Conclusion |
|---|---|
| `local_type=3` | Cached people such as group members; excluded from the ordinary-friend address book |
| `local_type IN (5,6)`, `@openim` | Enterprise contacts; the current API prioritizes suffix-based identification |
| `verify_flag & 8 != 0`, nonempty `biz_info.type` | Identifies official-account profiles; system entries take precedence, while the subtype still comes from `biz_info.type` |
| `flag & 2` | Not used to determine friendship |
| `(local_type,flag,verify_flag)=(1,3,0)` | Can apply to both individuals and groups; group identity still needs to be distinguished |
| `(local_type,flag,verify_flag)=(1,1,0)` | Can apply to ordinary people, the current account, system entries, and ClawBot; special identities still need to be excluded |

### `biz_info` table and NULL join boundaries

Actual column list: `id INTEGER PRIMARY KEY`; `username TEXT`; `type/accept_type/child_type/home_url/version/external_info/brand_flag` are INTEGER; `sync_version/brand_info/brand_icon_url/brand_list/belong` are TEXT; `ext_buffer BLOB`. Although the source column is named `home_url`, the schema declares it INTEGER; do not change its type based on its name.

Currently, only a LEFT JOIN on the complete `username` to `contact` is used, with `type` exposed as `official_type`. Existing samples support **0 = subscription account, 1 = service account**; values 2 and 3 are preserved, and the full set of categories is unconfirmed. No general enum has been confirmed for `accept_type`, `child_type`, or similar fields. `external_info` is declared INTEGER, but existing samples contain readable JSON with `ServiceType`; a SQLite declared type does not guarantee the runtime type of every value, so do not blindly convert it based on the declaration.

**`official_type` can be absent for two reasons: no matching `biz_info` row, or a matching row whose `type` is NULL.** The current LEFT JOIN selects only `b.type`; `kind` is based on the same value. Neither provides an independent indicator that a matching row exists.

### Group profiles and group nicknames

| Table | Actual columns | Verified use / unresolved items |
|---|---|---|
| `chat_room` | `id INTEGER PRIMARY KEY, username TEXT, owner TEXT, ext_buffer BLOB` | `username` identifies the group; the exact relationship of `owner` to the group-owner field has not been independently verified; `ext_buffer` has been parsed for member identity and group nicknames |
| `chatroom_member` | `room_id INTEGER, member_id INTEGER`; both UNIQUE | Member relationship table; the full mapping of these integers to IDs in other tables has not been independently verified. Current member reads do not rely on that inference |
| `chat_room_info_detail` | `room_id_ INTEGER PRIMARY KEY, username_ TEXT, announcement_ TEXT, announcement_editor_ TEXT, announcement_publish_time_ INTEGER, chat_room_status_ INTEGER, xml_announcement_ TEXT, ext_buffer_ BLOB` | Group announcement and detail fields; trailing underscores are part of the actual source names. Announcement time units and status enums are unverified, and not all fields are currently exposed |
| `contact_label` | `label_id_ INTEGER PRIMARY KEY, label_name_ TEXT, sort_order_ INTEGER` | Label and sort-order fields; the relationship to contacts has not been verified |

Protobuf structure of `chat_room.ext_buffer`: repeated member objects are top-level field 1; member field 1 is username and field 2 is group nickname. `group_nickname` is scoped to the group and member, and stored separately from global `nick_name`.

GroupMemberV2 exposes `room_username/username/group_nickname/display_name`. In-group display-name priority is **remark → group nickname → global nickname → username**. A NULL or empty `ext_buffer` returns an empty local member result.

| Source column | Meaning / handling | Current ChatV2 |
|---|---|---|
| `username` | Source conversation identifier; prefixes and suffixes are preserved | `username` |
| `unread_count` | Original integer; NULL remains null, and zero/negative values are not adjusted | `unread_count` |
| `unread_first_msg_srv_id` | Server ID field for the first unread message | Not exposed |
| `unread_first_pat_msg_local_id` | Local ID field for the first unread nudge message | Not exposed |

| `summary` | Source summary; both empty strings and NULL currently become null | `last_message_preview` |
| `last_msg_sender` | **Original source value**; may contain `_$_CUSTOM_USERNAME_PREFIX_$_…:…`, and is not split into an ordinary username | `last_msg_sender` |
| `last_sender_display_name` | Source display label; empty strings become null | `last_sender_display_name` |
| `last_timestamp` | Converted as Unix seconds; returned as RFC3339 only if positive and representable, otherwise null | `last_activity_at` |
| `last_clear_unread_timestamp` | Timestamp of the most recent unread-clear action; unit unverified | Not exposed |
| `last_msg_locald_id` | Source spelling includes `locald`; only the public spelling is corrected, not the value | `last_msg_local_id`, nullable JSON number; not a server_id |
| `last_msg_type` | Most recent message type field; relationship to packed message types is unverified | Not exposed |
| `last_msg_sub_type` | Most recent message subtype field; exact value mapping is unverified | Not exposed |
| `last_msg_ext_type` | Most recent message extension-type field; enum unverified | Not exposed |

| `is_hidden` | Currently selects only 0 | Used for filtering; not exposed |

| `draft` | Read by a legacy projection; content encoding unverified | Not exposed |
| `status` | Conversation status code; enum unverified | Not exposed |

Chat `display_name/remark/nick_name` come from the contact-name join; conversations without contact details are retained and fall back to username. Reading the conversation list does not open chats or clear unread counts. It is frozen independently from the contact list and is not an atomic cross-endpoint snapshot. `last_msg_local_id` remains a JSON number, which may exceed JavaScript's safe-integer range; no such oversized value has been verified yet.

## message_N.db: messages and identity

### Schema and relationships

The current implementation uses the MD5 of the chat username to locate the `Msg_<32 hexadecimal characters>` table, searching across validly numbered `message_N.db` files. `real_sender_id` joins to `Name2Id.user_name` through that shard's `Name2Id.rowid`; therefore, the API's `sender_username` is based on an actual JOIN, not merely a renamed numeric field.

`Msg_*` table fields:

| Source field | Declared type | Meaning / handling in this project |
|---|---|---|
| `local_id` | INTEGER PRIMARY KEY AUTOINCREMENT | Local row identity within this table, not a message identity global across conversations or shards |
| `server_id` | INTEGER | Native WeChat message identifier; this project uses it as the unique message key and media locator within the logged-in account |
| `local_type` | INTEGER | Packed message type; the low and high 32 bits are projected as `type` and `sub_type` respectively |
| `sort_seq` | INTEGER | Source ordering-related value; native lookup reads it as text. Exact generation and global-sequence semantics are unconfirmed |
| `real_sender_id` | INTEGER | Joins to this shard's `Name2Id.rowid` to obtain the sender's `user_name` |
| `create_time` | INTEGER | Currently interpreted as Unix seconds; it is not a trusted local database commit time |
| `status` | INTEGER | Status enum unconfirmed; do not use it to claim delivery |
| `upload_status` | INTEGER | Upload-status enum unconfirmed |
| `download_status` | INTEGER | Download-status enum unconfirmed |
| `server_seq` | INTEGER | Sequence semantics and relationship to `server_id` are unconfirmed |
| `origin_source` | INTEGER | Source enum unconfirmed; do not infer manual/automatic origin from the name |
| `source` | TEXT | Additional message data; currently decoded for values such as `atuserlist`, not display content |
| `message_content` | TEXT | Raw stored content may contain text, XML, or compressed bytes; do not skip decompression based only on the declared TEXT type |
| `compress_content` | TEXT | Observed column; relationship to the WCDB compression flag is unverified, and current reads do not depend on it |
| `packed_info_data` | BLOB | Observed column; format not fully parsed |
| `WCDB_CT_message_content` | INTEGER DEFAULT NULL | The implementation decompresses content based on a nonzero value and Zstd magic; the complete flag enum is unverified |
| `WCDB_CT_source` | INTEGER DEFAULT NULL | Corresponding decode marker for `source`; do not conflate it with the content marker |

The source table's `server_id` index is not a UNIQUE constraint; the unique message key used by business logic is separate from the database-declared constraint. `Name2Id.rowid` values are independent across shards/databases.

### `server_id`, `local_id`, and API lookup

- **server_id**: Exposed as a decimal string to avoid JavaScript `Number` precision loss. Current lookup accepts canonical, nonzero values parseable as signed i64; it does not take absolute values or change the source type based on another project's `uint64` declaration.
- **local_id**: Also exposed as a string, but only identifies a row within a table. The same number can occur in different chats/shards; converting it to a string solves precision loss, not ambiguity.
- All verified API messages for the logged-in account have nonzero `server_id` values, with no duplicates across the conversations read; business logic therefore uses `server_id` as the message key.
- V2 returns null for missing/zero message IDs. Cross-import matching uses native message identity, not `local_id` or guessed matches based on equal text/timestamps.
- `/api/v2/messages/{server_id}` accepts optional `chat_username` to narrow the search; the server checks all relevant shards in the current account. Multiple matches return an explicit ambiguity error rather than the first result; a partial shard-read failure is not treated as proof of absence.
- Media and raw voice use the same internal source-row anchor. Do not look up a `local_id` by `server_id` and then call an old path that arbitrarily selects the first shard.
- The legacy CLI `<chat> <localId>` syntax is compatibility input only: complete pagination must find exactly one record and release the sample before using its actual nonzero `server_id`. Missing IDs, ambiguity, or pagination failure must not be handled by fabricating an ID.

### Stored content, compression, and direction

| V2 field | Source and semantics |
|---|---|
| `raw_type` | Full original `local_type` as a decimal i64 string, without truncation |
| `type/sub_type` | Low/high unsigned 32 bits of `raw_type`; do not conflate with `contact.local_type` |
| `xml_sub_type` | Independently parsed from body `appmsg/type`; does not overwrite the source value even if it conflicts with the packed subtype |
| `raw_content` | Hexadecimal **stored bytes** of `message_content`; not the ciphertext of the entire SQLCipher database, and not necessarily decompressed |
| `raw_content_compression` | Required boolean paired with `raw_content`; absence does not default to false and must be preserved by decoders |
| `content` | Content after decoding, group-prefix handling, and display cleanup; may contain only a title/link summary and is not a substitute for the original bytes |
| `timestamp` | RFC3339 time; null if outside the representable range. Collection fails if source `create_time` is missing or non-integer |
| `sender_username` | `user_name` obtained by the `Name2Id` JOIN; may be null if no match exists |
| `sender_display_name` | Display name derived from contact fields, not the original `real_sender_id` |
| `is_self` | Derived marker indicating whether the current account sent the message; current code prefix-matches the sender against the account directory. See the next section for the account identity source |
| `is_mentioned` | True when a group `atuserlist` match is found; currently null when not found, not false |

`source` and message content each have their own compression marker; V2 preserves the original content hex/boolean. `create_time` is message time and is not used to measure local “database write → notification” latency.

### Current logged-in account and `is_self`

The canonical account value exposed externally is **`account_username` returned by `GET /api/v2/account` when `status=logged_in`**; it is null in other states. `expected_account_username` expresses the caller's intended account; it is not an identity source.

The internal chain is: login session record → unique WeChat process and its open account database directory → `ReadIdentity.account_id` → `account_username`. Current `account_id` is derived by `derive_account_id`, which removes the installation suffix after the last underscore in the account directory name. The account endpoint also checks UI login state and the scope before and after observation.

`sender_username` comes from the message shard's `Name2Id` mapping. Current `is_self` uses `account_dir.starts_with(sender)` rather than exact equality between `sender_username` and `account_username`. This is a precision limitation in the current implementation; `is_self` must not be used as proof of account identity. No native self field independent of directory naming has been verified as a substitute. This documentation update does not change runtime direction detection.

**filehelper:** Its exact username is `filehelper` and its kind is system. Both messages manually sent from the phone and messages sent by the program can have the current account as sender and `is_self=true`; `is_self` does not distinguish manual from automated sends. The outbox is confirmed to suppress this program's own echoes by account + chat + server_id; unmatched messages remain unattributed. ClawBot uses the complete account-specific `@weclaw` identifier and is not matched across accounts by nickname or a fixed full username.

### Three message-type dictionaries

The single code dictionary is `packages/agent-server-rust/src/message-type-dictionary.json`, returned by `/api/v2/message-types` and used to generate shared/CLI labels; unknown numeric values are preserved. The following is the currently covered range, not a closed enum.

| Namespace | Values and labels |
|---|---|
| Main type `type` | 1 text; 3 image; 34 voice; 37 friend-request details; 42 contact card; 43 video; 47 sticker; 48 location; 49 app message; 50 call; 51 status sync; 64 group-call invitation; 10000 system notice; 10001 interaction/security notice; 10002 revoke notice |
| App XML type `appmsg/type` | 3 music; 4 video link; 5 link; 6 file; 19 merged forward; 33, 36 mini program; 57 quote; 62 nudge |
| Forwarded entry `datatype` | 1 text (included); other numeric values are retained and not misrepresented as main message types |

The dictionary's `basis` distinguishes `default_adopted` from `local_observed`: current main-type entries use the former; app type 57 and forwarded-entry type 1 use the latter. Other app entries are adopted by default, which does not mean all have been verified against a live client. The full semantics of app types 1 and 24 remain unconfirmed; type 24 may use a `recorditem` structure and cannot be declared equivalent to the supported type 19. App type 4 must not be reclassified as type 5 merely because its display includes a URL.

### Quote and merged-forward XML

| Source XML | API / interpretation |
|---|---|
| `refermsg/svrid` | Original string value in `reference.server_id`; may be `"0"`, which is not a usable nonzero ID for lookup |
| `refermsg/chatusr` | `reference.sender_username`, the quoted author; do not guess the outer author if absent |
| `refermsg/fromusr` | Source conversation for a group quote; falls back to the current group if absent, while direct chats use the current chat. Exposed as `reference.chat_username` |
| `refermsg/displayname` | Display name at the time of the quote; do not replace it with the contact's current remark |
| `refermsg/content` | Text parsed from XML; quote content is retained, but complete rendering of deeply nested messages is not guaranteed |
| `recorditem` | `recordinfo` XML may be embedded in the outer XML text; parse one layer at a time, handling CDATA/escaping without repeatedly applying global unescape |
| `recordinfo/datalist/dataitem` | Ordered forwarded entries; the outer forwarder is not the author of every inner message |
| `dataitem` attributes `datatype/dataid` | Preserve entry type and ID; `datatype` belongs to a separate namespace |
| `datadesc/sourcename/sourceheadurl/sourcetime` | Original text / display name at the time / avatar source / display time; URLs are not downloaded automatically and time zones are not inferred |
| `srcMsgCreateTime/fromnewmsgid` | Strings exposed as `src_msg_create_time/from_new_msg_id`; inner messages are not guaranteed to exist in the current account database |
| `dataitemsource/hashusername` | Original value exposed as `dataitem_source_hash_username`; do not present a hash or display name as a real username |

`forwarded_record` is returned only for supported structures; `parse_status` is complete/truncated/invalid. Limits are 4 MiB input, depth 16, 20,000 nodes, 100 entries, and 64 KiB for `datadesc`. The `datadesc` limit is checked after text materialization and is not a pre-allocation memory limit. DTD/external entities are prohibited; unknown structures or duplicate single-value elements must not be silently discarded and reported as complete. Inner entries are never automatically executed as independent incoming messages.

## Media databases and file indexes

The following are **columns used by the source code**. No additional columns are listed for tables without evidence of their complete actual schema.

| Database / table | Fields | Relationships and contents |
|---|---|---|
| `media_N.db / Name2Id` | `user_name, rowid` | Find this media shard's conversation row ID using the chat username |
| `media_N.db / VoiceInfo` | `chat_name_id` | Refers to `Name2Id.rowid` in this media database, not the sender row ID in a message shard |
| Same | `svr_id` | The raw-voice path matches this value against the message `server_id` |
| Same | `local_id` | The existing generic media implementation also has a `local_id` lookup path; this does not make `local_id` a global identity or invalidate the verified `svr_id` path |
| Same | `create_time` | Used to recheck consistency of the raw-voice anchor |
| Same | `voice_data, rowid` | Audio BLOB and media-row locator; the dedicated voice endpoint returns SILK, while generic media may convert to MP3 |
| `message_resource.db / ChatName2Id` | `user_name, rowid` | chat username → internal chat ID in this resource database |
| `MessageResourceInfo` | `chat_id, message_local_id` | Resource record located by resource-database chat ID + local message ID |
| Same | `packed_info` | Binary resource metadata; current parsing extracts the file hash, but the full layout is not parsed |
| `hardlink.db / image_hardlink_info_v4` | `md5, file_name, dir1, dir2` | Look up candidate filenames and directory keys using the message XML MD5 |
| `hardlink.db / dir2id` | `rowid, username` | Directory key → path component; do not interpret this `username` directly as a contact account |

`Name2Id` row IDs in message and media shards are independent. `server_id → svr_id` is a verified raw-voice relationship; callers do not need to provide `chat_name_id`, and this does not prove internal conversation conditions can be removed.

Common image candidates use `_t.dat` for thumbnails, `.dat` for standard images, and `_h.dat` for originals; suffixes do not guarantee complete bytes or that the client downloaded the file. File-message attachments are checked locally using XML title/fileext and size/MD5; an index match does not mean the file is present on disk. Video results may contain only a JPEG cover/thumbnail, and location messages may return a map preview; `type=video` does not guarantee that `data` is the video itself, and an omitted quality does not guarantee the original. Location coordinates/place may remain in content XML and are not currently exposed as an independent structured location object.

Media `pending` means it cannot be delivered yet; an empty image is not reported as success. `unsupported` may also mean the account/message is unavailable and does not by itself prove WeChat lacks support. See the API documentation for native-transfer and wait behavior; download parameters in resource tables or messages must not automatically be treated as usable URLs.

## Source databases, WAL, and two kinds of snapshots

WeChat databases are SQLCipher-encrypted. The current reader collects source DB/WAL bytes as ordinary read-only files; it does not connect to the live WeChat source with SQLite or copy the source SHM. SQLCipher opens a private encrypted mirror. WAL merging includes only the prefix that passes standard salt, checksum-chain, and commit-boundary validation. Physical remnants beyond an invalid prefix are not automatically treated as valid commits; this also does not prove that all recent messages have been found.

| Mechanism | What is retained | Lifetime and budget |
|---|---|---|
| Reuse of isolated source mirror | Complete private encrypted mirror, not a persistent plaintext database | Reused while source DB/WAL metadata and keys remain unchanged; rebuilt when they change. Independent connection per request; four-entry cache. Per-operation processing budget is 512 MiB, not a process RSS limit or permission for a 512 MiB main database |
| API frozen pagination | In-memory set of collected rows | Nonrenewable 300-second TTL, four slots, 50,000 rows/16 MiB per sample, 32 MiB total, 3 MiB per page. Continuations do not rescan the source; release deletes the in-memory sample, not source files |

`data_changed` is only a DB/WAL file-change hint and may occur before transaction commit; it is not a reliable message queue with message IDs. The current implementation uses source isolation. The previously tried direct-SQL read path has been discontinued; passing generic synthetic SQLite tests is not a reason to resume direct reads from a live source.

## Evidence and maintenance boundaries

Current field implementation entry points: `tools/wechat_contacts.rs`, `wechat_group_members.rs`, `wechat_chats.rs`, `wechat_messages.rs`, `message_record.rs`, `wechat_media.rs`, and `wechat_read_voice.rs`. Public types are defined in `ia/types.rs`, and routes in `router/read_v2.rs` (all under `packages/agent-server-rust/src/`). Keep database source fields, API-derived fields, and downstream business decisions documented separately.

This page summarizes existing safe copies and source-code review; no live source was accessed and no friendship relationships were changed to write it. When adding fields, state the client version, actual schema/runtime value types, semantic evidence, and whether a claim is inferred only from samples. Keep unverified databases and fields marked “unconfirmed”; do not present limited copies as a complete official protocol.

## Reading and exporting

### Through the API/CLI

Prefer the existing API/CLI:

```bash
# Conversation list
wx chats list --json

# Messages
wx messages list <chatId> --json

# Retrieve media by native message ID
wx messages media <chatId> --server-id <serverId> --output photo.jpg
```

### Access files through Docker volumes

The following are file-access commands only, **not a consistent backup of a running database**. Before history migration, coordinate consistent backups of both volumes and the associated application ledger; see [User Guide](/operations/user-guide#desktop-access-and-history-import). Verify the actual mounts; the example volume names do not apply to every deployment.

```bash
# Inspect a volume
docker volume inspect agent-wechat-data

# Copy files from the container
docker cp agent-wechat:/data/agent.db ./agent.db
docker cp agent-wechat:/home/wechat/ ./wechat-data/
```

### Observe through VNC

Use `http://localhost:6174/vnc/` with an authenticated token to view the WeChat interface. File presence, API responses, and what the client actually displays are different levels of evidence.

## Disk space

Messages, media, and caches grow with use. Check volume usage with:

```bash
docker system df -v | grep agent-wechat
```

For low disk space, see [Disk space troubleshooting](/reference/troubleshooting#disk-space).
